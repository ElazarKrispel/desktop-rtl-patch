# Desktop RTL: חוות דעת אסטרטגית והיערכות להפצה

**תאריך:** 7 בספטמבר 2026  
**ריפו:** `ElazarKrispel/desktop-rtl-patch`  
**נקודת הבדיקה:** `02cc70a8b750de4bc88b740cf8a64f292a5c0325`  
**גרסה שנבדקה בקוד ובמטאדאטה:** `v2.5.0`, שפורסמה ב־6 בספטמבר 2026  
**סוג העבודה:** סקירת קוד ממוקדת סיכונים, ניתוח מוצר וארכיטקטורה, מחקר תיעוד רשמי ובדיקה מבודדת אחת. אין כאן אישור אבטחה או אישור E2E ל־Windows.

## 1. ההחלטה המומלצת

**להמשיך בפרויקט, אבל לא לפתוח בשכתוב כולל ולא להתחיל עדיין בהפצה רחבה למשתמשים לא־טכניים.** הבסיס שימושי ויש בו השקעה הנדסית אמיתית. הפער המרכזי הוא מעבר מכלי שהמפתח יודע לתפעל למוצר שמתנהל באמינות גם כשנכשלת התקנה, משתנה גרסת המקור או המשתמש לא יודע היכן נמצאים הקבצים.

הסדר המומלץ הוא: **תיקוני בטיחות ואמינות → בטא מוגדרת → מנהל Windows עצמאי → הרחבת תמיכה לפי ביקוש.**

המוצר הרצוי הוא מנהל תאימות מקומי לעבודה בעברית בכלי AI קיימים. הוא מזהה אפליקציות, מסביר מה ניתן לתקן, מתקין התאמה בטוחה, יודע לאבחן ולחזור לאחור ומציג באופן ברור מה נבדק. הוא אינו צריך להפוך ללקוח צ'אט חדש או לנהל את חשבונות ה־AI של המשתמש.

קיימת כבר גרסה ציבורית, ולכן השאלה המעשית היא מוכנות לקידום ולהורדות של משתמשים חדשים, ולא רק שינוי הגדרת הריפו מ־private ל־public. [R1]

### היקף הבדיקה וגבולות הביטחון

נבדקו דרך חיבור GitHub קובצי המקור המרכזיים, ענפים, פרטי ה־release, תהליך אריזה, דיון PR מספר 6 ומידע על הרצות Actions. נקראו מסלולי ההתקנה, העדכון, ההסרה, הניהול במגש, ההזרקה, ההגדרות והאבחון. מקורות הקוד במסמך מקושרים ל־commit שנבדק, ולא למצב עתידי של `main`.

לא הורצו כאן Windows PowerShell 5.1, האשף, לקוחות ה־AI האמיתיים או חבילת ההורדה על מחשב Windows נקי. ה־ZIP לא אומת עצמאית ברמת הבתים: נבדקו קוד האריזה והמטאדאטה ש־GitHub מפרסם. דיווחי הבדיקות ב־PR הם דיווחי המפתח, לא תוצאות שהופקו מחדש במסגרת סקירה זו. [R2]

כן הורצה בדיקת Node מבודדת של פונקציית `doFuseOff`, על נתוני דמה ותיקיות זמניות ב־Linux. היא הראתה שהגנת הנתיב מאפשרת כתיבה אל יעד פיזי מחוץ לשורש דרך symbolic link. הבדיקה אינה תחליף לבדיקת junction ב־Windows או להוכחת פגיעות של כל שרשרת ההתקנה.

## 2. מה כבר בנוי היטב וכדאי לשמור

אין כאן רק אוסף סקריפטים ללא מבנה. יש פרופילים למספר אפליקציות, כמה אסטרטגיות התאמה, מנגנון staging והחלפה, סוכן רקע מאוחד, חסימת ניסיונות חוזרים לפי חתימת מקור וגרסת כלי, שגיאות מתורגמות, אשף WinForms, הגדרות וייצוא אבחון שמסנן נתיבים וסודות נפוצים. [R3] [R4] [R5] [R6]

גם במנוע הטקסט יש החלטות ראויות: שימוש ב־`dir`, בידוד קוד ומתמטיקה, הבחנה בין משטחי טקסט ועורכי קוד, ואיגוד אירועי DOM באמצעות `Set` ו־`requestAnimationFrame`. אין הצדקה לתאר אותו כמנוע שסורק תמיד את כל המסמך בכל הקשה. [R7]

לאשף כבר יש טיפול ב־DPI, פריסה מבוססת `TableLayoutPanel`, טקסטים בעברית ופעולות אבחון. ההמלצה לשדרוג UX אינה נובעת מכך שאין GUI, אלא מכך שהממשק עדיין מציג את תהליך התחזוקה הטכני במקום להוביל משתמש חדש לתוצאה. [R5]

**מה לשמר:** ידע ההתאמה הספציפי לכל אפליקציה, ה־renderer הקיים כבסיס, מקרי הבדיקה, מנגנוני staging וההתאוששות שעובדים, והאבחון המסונן. לא לתרגם אוטומטית כל PowerShell ל־C# לפני שמוגדרים חוזים ובדיקות.

## 3. ממצאים שמצריכים טיפול לפני הפצה רחבה

העדיפויות כאן הן עדיפויות שחרור מוצריות, לא דירוג CVSS. "ממצא בקוד" אינו אומר שהתרחיש הופעל במערכת Windows של המשתמש.

### F01. הגנת הכתיבה בודקת מחרוזת נתיב, לא יעד פיזי

**עדיפות:** חסם הפצה רחבה. **ראיה:** קוד + שחזור מבודד.

`Assert-RtlWriteAllowed` ו־`ConvertTo-RtlCanonicalPath` משתמשות ב־`GetFullPath`; ב־`doFuseOff` יש `path.resolve` ובדיקת prefix עם מפריד. זה מגן מפני נתיב רגיל מחוץ לתיקייה, אך לא מפני תיקייה בתוך staging שמפנה פיזית החוצה. [R3] [R8]

בבדיקה המבודדת, נתיב חיצוני ישיר נדחה עם קוד 22 והקובץ נשאר ללא שינוי. אותו קובץ דמה דרך קישור שבתוך staging שונה בהצלחה בבייט אחד. לא נגעו קובצי אפליקציה אמיתיים.

**התיקון:** מדיניות מפורשת ל־reparse points, פתרון נתיבים פיזיים, בדיקה של רכיבי הנתיב ושימוש ב־staging שנוצר ומנוהל בידי הכלי. יש לטפל גם בפער בין בדיקה לפתיחת הקובץ, ולא להסתפק ב־`realpath` חד־פעמי. ב־Windows קיימים ממשקים לפתרון הנתיב הסופי מתוך handle; hard links דורשים שיקול נפרד, משום שגם שמות שונים יכולים להפנות לאותו קובץ. [W1] [W2]

**קבלה:** בדיקות Windows על junction, symlink, שורש שהוחלף, prefix דומה וקישור לקובץ; יעדים חיצוניים נשארים byte-identical. אין להסיק מכאן הסלמת הרשאות: ההרשאות והשרשרת המלאה לא נבדקו.

### F02. הסרה חלקית יכולה לאבד את הדרך לתקן את עצמה

**עדיפות:** חסם בטא נוחה. **ראיה:** ניתוח זרימת קוד.

`Invoke-CodexRtlUninstall` ממשיכה להסרת קיצורים, state ו־config גם כשמחיקת עץ האפליקציה נכשלה חלקית. `Get-RtlInstalledApps` מונה אפליקציה רק כאשר קובץ ההפעלה קיים. אם דווקא ה־exe נמחק אך קובץ אחר נשאר נעול, האפליקציה יכולה להיעלם מהמגש; בהיעדר מקור, גם האשף עלול לא להציג אפשרות להסרת השאריות. [R3] [R5] [R6]

**התיקון:** installation receipt עמיד ומצב `CleanupPending` שאינם תלויים בקיום exe. להסיר את הרישום הניהולי רק לאחר השלמת כל מחיקות הקבצים והרישומים. שאריות צריכות להישאר נגישות ל"השלם הסרה" גם אחרי הפעלה מחדש וכשהמקור כבר לא מותקן.

**קבלה:** נועלים קובץ שאינו exe, מתחילים הסרה ומוודאים שה־exe אכן נמחק. מפעילים מחדש את המנהל: השאריות עדיין מוצגות. משחררים את הנעילה ומסיימים הסרה מה־GUI, לא רק בקריאה ישירה לפונקציה.

### F03. Herdr: נתונים פרטיים נמחקים בניגוד להודעת האשף

**עדיפות:** חסם הפצה של התאמת Herdr. **ראיה:** קוד והודעות UI.

התאמת Herdr משתמשת ב־config וב־session פרטיים. במסלול `prebuilt`, ההסרה מוחקת כברירת מחדל את תיקיות `data` ו־`state`. מנגד, הודעת ההסרה המשותפת באשף אומרת שנתוני ההתחברות והמטמון יישמרו ומציגה אותם כמשותפים למקור. תיאור זה אינו מתאים ל־Herdr. [R3] [R5] [R9]

**התיקון:** מדיניות נתונים לכל adapter. "קובץ נוצר אצלנו" אינו שקול ל"מותר למחוק אותו בלי לשאול". ברירת מחדל: הסרת תוכנה ושמירת מידע בעל ערך למשתמש. מחיקת פרופיל פרטי דורשת בחירה נפרדת והסבר מדויק. אין להחזיר אפשרות Purge לפרופילים משותפים רק כדי לעמוד בתכנון הישן.

**קבלה:** config מותאם אישית ו־session נשמרים בהסרה רגילה ובהתקנה מחדש; נמחקים רק במסלול שבחר המשתמש. בדיקה נפרדת לפרופיל משותף, פרטי ולא־ידוע.

### F04. חוזה התוצאות אינו אחיד: "לא נזרקה שגיאה" עדיין יכול להתפרש כהצלחה

**עדיפות:** חסם בטא נוחה. **ראיה:** קוד.

כאשר `Enter-RtlLock` נכשל, `Invoke-CodexRtlUpdate` רושמת הודעה ויוצאת ללא תוצאת פעולה מפורשת. האשף ממשיך למסלול הצלחה לאחר הקריאה. זו אינה הוכחה לתוצאה שהוצגה בפועל במחשב, אבל זה מסלול שבו פעולה שלא בוצעה אינה נבדלת היטב מהצלחה. [R3] [R5]

בהסרה מהמגש, `Start-AppUninstall` מפעילה PowerShell נפרד ומוסתר ומציגה "מסיר את ההתקנה...". לא נמצא שם ערוץ שמחזיר ל־UI את תוצאת הסיום, exception או רשימת `Leftovers`. יצירת תהליך אינה אישור להשלמת הסרה. [R6]

**התיקון:** תוצאה מובנית ואחידה ל־GUI, CLI, tray ו־worker: `Succeeded`, `AlreadyCurrent`, `Deferred`, `Busy`, `Blocked`, `Partial`, `Failed`, בצירוף קוד שגיאה, מזהה פעולה, שאריות והנחיית התאוששות. פעולות רקע צריכות להגיע למצב סופי בר־תצוגה גם אם החלון המקורי נסגר.

**קבלה:** החזקת lock אינה מציגה הצלחה; הסרה חלקית מהמגש מציגה כשל ושאריות; פעולה שנדחתה כי האפליקציה פתוחה מוצגת כ"מוכן להחלה" ולא כ"עודכן".

### F05. כשל רשת זמני ב־Herdr עלול להפוך לחסימה מתמשכת

**עדיפות:** לפני הפצה של Herdr ועדכון אוטומטי רחב. **ראיה:** שילוב שני מסלולי קוד.

`Resolve-HerdrRtlArtifact` ממפה כשלי הורדה ל־`[ARTIFACT]`. במנוע הראשי, `[ARTIFACT]` נחשב לכשל מבני שננעל לאחר שתי הופעות באותה חתימה וגרסת כלי. לכן שתי תקלות רשת אינן בהכרח מתאוששות כשהחיבור חוזר: ה־Auto עשוי כבר להיות חסום. [R3] [R9]

**התיקון:** להפריד בין Network/Timeout/RateLimit לבין חבילת build לא תואמת ואימות תקינות שנכשל. תקלות זמניות מקבלות backoff עם מועד ניסיון הבא, תקציב ניסיונות ו־jitter; כשל מבני מזוהה נשאר חסום. לא להסיר את ההגנה מפני retry storm.

**קבלה:** אחרי שתי נפילות רשת ואז התאוששות, ההתקנה מתאוששת אוטומטית בלי Force; חבילת checksum שגויה לעולם אינה מותקנת; כשל מבני חוזר אינו גורר העתקות בלתי מוגבלות.

### F06. Launcher שנכתב ב־ASCII אינו מתאים לנתיבי משתמש בעברית

**עדיפות:** לפני בטא לדוברי עברית. **ראיה:** קוד; Windows E2E נדרש.

`New-RtlLaunchScript` כותבת ב־`ASCIIEncoding` קובץ VBS שמכיל נתיבי exe ותיקיית עבודה. נתיבי Windows יכולים להכיל שם משתמש בעברית; ההנחה שהקובץ מכיל "רק נתיבים ושמות environment" אינה מבטיחה ASCII. המסלול רלוונטי לפרופילים עם `LaunchEnv`, ובהם Grok Bot. [R3]

**התיקון הקצר:** פורמט Unicode ש־WSH קורא כראוי, עם בדיקה על מחשב נקי. **התיקון הארוך:** launcher בינארי שמוסר argv וסביבת תהליך בלי לייצר קוד VBS עם נתיבים משובצים.

**קבלה:** פתיחה מקיצור וממגש במשתמש ששמו בעברית, נתיבים עם רווחים, OneDrive ותיקיות מופנות. להשוות גם את סביבת תהליך הילד, לא רק את קיום הקיצור.

### F07. הבטחות הבטיחות והתאימות ב־README אינן מסונכרנות עם v2.5.0

**עדיפות:** לפני קידום ציבורי. **ראיה:** תיעוד מול קוד.

ה־README עדיין מתאר את Codex כמצב שבו עורכים רק `app.asar` ו־asar-integrity כבוי מראש. הקוד ב־v2.5.0 משנה גם בייט ב־`chrome.dll` של העותק כדי לכבות את האימות. Electron מתעדת את ASAR Integrity כמנגנון לאימות הארכיון בזמן ריצה. שינוי בעותק בלבד הוא הבחנה חשובה, אך אינו אומר שאין שינוי בתכונת אבטחה בעותק. [R3] [R8] [R10] [W3]

כמו כן, FAQ גורף על פרופיל משותף אינו נכון ל־Herdr; ההצהרה שאין הפצת קוד של אפליקציות דורשת הבחנה מהתקנת build של fork; גודל ZIP המתואר הוא 285 KB בעוד מטאדאטת v2.5.0 מציגה 1,026,766 בתים. [R1] [R9] [R10]

**התיקון:** טבלת "מה משתנה" לכל אפליקציה: קובצי התקנה, מנגנוני אימות, פרופיל משותף/פרטי, קיצורים, COM/פרוטוקולים, עדכונים ורמת הבדיקה. להחליף הבטחות מוחלטות בתיאור מדויק. לא מוצגת כאן מסקנה משפטית; את רישיונות ה־fork וה־notices צריך לבדוק בנפרד לפני הפצת builds נוספים.

### F08. ניהול state וסביבת תהליכים צריך הקשחה, לא רק פיצול קבצים

**עדיפות:** במהלך ריפקטורינג המנוע, לפני הוספת מקביליות.

`Get-CodexRtlStatus` עדיין משנה state כאשר הוא מעביר JSON פגום ל־`.bad`. `Write-RtlState` ו־`Write-RtlConfig` כותבות ישירות, בעוד agent config כבר משתמשת בהחלפה עם temp ו־backup. יש כאן חוסר אחידות. בנוסף, `Set-RtlActiveApp` משנה environment של התהליך, בזמן שיש UI ו־runspaces; פעולות במגש שומרות ומשחזרות אותו, אך זו אינה הוכחת בידוד בין פעולות מקבילות. [R3] [R6]

**התיקון:** status טהור; quarantine ותיקון במסלול פעולה נעול; כתיבה אטומית לכל רשומות המצב; `AppContext` מפורש; environment נפרד לכל child process; mutex נפרד וברור לפעולות כלל־המערכת כגון החלפת agent. לא להציג race בתור באג ששוחזר: זהו סיכון ארכיטקטוני שמצריך בדיקה.

### F09. מנוע ה־RTL צריך חוזי התנהגות ורגרסיות של אפליקציה מודרנית

**עדיפות:** תיקונים ממוקדים לפני בטא, הרחבת הכיסוי בהמשך.

ב־`processAll`, קריאה ל־`processLeafContainers` אינה מותנית ב־`S_PROSE`; לכן כיבוי משטח prose לא מבטיח שגם div/span/label לא ישונו. טבלה שכבר סומנה RTL מדולגת בבדיקות הבאות, ולכן יש לבדוק שימוש חוזר באותו DOM עם תוכן אנגלי. [R7]

`isolateMath` מחליפה text nodes ב־fragments. אין כאן שימוש ב־innerHTML, אבל זה עדיין שינוי של מבנה DOM שייתכן שה־framework מנהל. React עצמה מזהירה ששינוי ילדים שהיא מנהלת עלול ליצור אי־עקביות או קריסות. לא שוחזרה כאן קריסה באפליקציות היעד. [R7] [W4]

**התיקון:** בדיקות של streaming, rerender, טבלאות ממוחזרות, paste/undo/selection, שדות קלט, Markdown וקוד. מצב safe mode שמסתפק בשינויי direction ו־CSS מצומצמים ומשבית rewriting מבני בעייתי. לא ליישם את אלגוריתם Unicode מחדש באמצעות היפוך מחרוזות; לשמור על logical order ועל בידוד מקומי. [W5]

### F10. תהליך השחרור צריך להיות שער איכות ניתן לשחזור

**עדיפות:** לפני קידום ציבורי רחב.

נמצאו קובצי בדיקה ודיווחי בדיקות ב־PR. לעומת זאת, endpoint הרצות GitHub Actions החזיר אפס הרצות. `Build-Release.ps1` אורז ומחשב checksum, אבל קובץ חסר ברשימת ההכללה גורר warning ולא בהכרח כשל אריזה. אין להסיק מכך שלא נעשו בדיקות מקומיות; כן חסרה שרשרת build/test ציבורית שניתן לבדוק מחדש. [R2] [R11] [R12]

מנגנוני ההורדה מאמתים checksum באמצעות חיפוש digest בטקסט, בלי לקשור אותו במפורש לשם הקובץ. בחירת ZIP לעדכון מבוססת על סיומת כללית. אלה החלטות שראוי לחזק לפני הוספת ארכיטקטורות או חבילות נוספות. [R3] [R9]

**התיקון:** exact asset name + version + architecture; parser לרשומת checksum של אותו קובץ; חתימות עדכון; build מ־commit מוגדר; פקודות בדיקה אחידות; artifact attestations; immutable releases עתידיים. GitHub תומכת בשני האחרונים, אך הפעלת immutability אינה משנה בדיעבד releases ישנים. [W6] [W7] [W8]

## 4. הארכיטקטורה שאליה כדאי להתקדם

### עיקרון: הממשק לא יודע לבצע מחיקות

ה־UI צריך לבקש פעולה מתועדת, לא להרכיב PowerShell חופשי או להחליט אילו מפתחות Registry למחוק. המנוע צריך להיות ניתן להרצה ולבדיקה בלי UI.

החלוקה המומלצת:

| שכבה | אחריות |
|---|---|
| מנהל Windows | זיהוי משתמש, מסכי מצב, הסכמה, progress, הגדרות ואבחון |
| חוזי פעולות | schema לגרסאות, בקשות, תוצאות, שגיאות, progress ו־cancellation |
| מנוע התקנה | תכנון, locks, staging, אימות, החלה, rollback ו־cleanup |
| adapters | גילוי מקור, תאימות, דרך הזרקה, פרופיל, רישומי מערכת ופתיחה לכל אפליקציה |
| מנוע RTL | לוגיקת טקסט/DOM נפרדת, ללא גישה לקבצים או ל־Registry |
| שכבת שחרור | הורדה, חתימות, ערוצים, provenance ומטריצת תאימות |

כל adapter צריך לספק פעולות כמו `Detect`, `AssessCompatibility`, `Plan`, `Apply`, `Verify`, `Launch`, `Uninstall` ו־`ListOwnedArtifacts`. אין צורך שכל API יהיה מורכב; חשוב שכל אחד יחזיר נתונים במקום לשנות global state.

### Installation receipt ומודל מצב

לכל התקנה יש לשמור מזהה, מקור וחתימה, גרסת adapter ו־payload, רשימת artifacts בבעלות הכלי, מדיניות פרופיל, מצב הפעולה האחרונה, שאריות וגרסה קודמת שניתן לחזור אליה. receipt נשמר גם אם exe נעלם.

יש להפריד שלושה ממדים: **קיום התקנה**, **בריאות ההתאמה** ו־**מצב העדכון**. אפליקציה יכולה להיות מותקנת, פעילה בגרסה הישנה, ובו־זמנית חסומה מול גרסה חדשה. מחרוזת יחידה "מעודכן" אינה מבטאת את זה.

החלפת המנוע תיעשה adapter אחד בכל פעם. בתקופת המעבר אפשר לארח את ה־CLI הקיים כתהליך נפרד שמדבר JSON lines. stderr מיועד ללוגים; stdout מיועד לאירועים ולתוצאה על פי schema. אין להפעיל סקריפט שמורכב מטקסט שרירותי שהגיע מ־UI.

### נפח דיסק וביצועים: זו החלטת מנוע, לא בחירת GUI

החלפה של WinForms ב־WPF או ב־Tauri אינה מבטלת את הצורך בהעתקת האפליקציה. אסטרטגיית copy/staging היא שקובעת את רוב נפח הדיסק וה־I/O במסלול הזה. יש למדוד בנפרד עלייה וצריכת משאבים של המנהל, זמן העתקה והזרקה, ותגובתיות של ה־renderer. [R3]

לשפר קודם הימנעות מעבודה מיותרת, שימוש מחדש ב־staging מאומת, סגירת לופים של כשל וניקוי גרסאות ישנות לפי מדיניות בטוחה. לא להשתמש ב־hard links בין המקור לקבצים שהכלי משנה כדי "לחסוך העתקה": שמות שונים אינם מבטיחים קבצים נפרדים. [W2] יעדי זמן, CPU ו־RAM ייקבעו לאחר baseline; אין בדוח benchmark שמצדיק הבטחה מספרית.

## 5. הסטאק המומלץ

**ברירת המחדל שלי למוצר הנוכחי: C# עם .NET 10 ו־WPF, בגישת MVVM, למנהל Windows.**

הסיבה היא שהחלק הקשה כאן הוא Windows: Registry, תהליכים, קיצורים, קבצים, locks, autostart ו־recovery. WPF מספקת מסגרת Windows עם פריסה, binding, templates ותמיכה בכיווניות. .NET 10 היא גרסת LTS נתמכת; אין סיבה להתחיל מוצר חדש על runtime ישן רק משום שהסקריפטים עובדים ב־PowerShell 5.1. [W9] [W10]

אין חובה שהממשק ייראה מיושן. אפשר ליצור UI נקי באמצעות styles/templates, ו־WPF כוללת גם מסלול Fluent. יש לבדוק את הרכיבים שנבחרו, RTL, accessibility ו־DPI; תיעוד .NET 10 מציין שתמיכת Fluent עדיין משתפרת, ולכן אין להניח אפס באגים או שכל API חדש הוא יציב. [W11]

| חלופה | מתי היא מתאימה | החלטה מוצעת |
|---|---|---|
| PowerShell + WinForms הקיים | תיקוני בטיחות ובטא מהירה ללא החלפת כל המערכת | לשמר זמנית ולנקות את מסך הכניסה |
| C# / .NET 10 / WPF | מנהל Windows מקומי שהאינטגרציה למערכת ההפעלה מרכזית בו | הבחירה המומלצת למעטפת העצמאית |
| Tauri 2 + Rust + React/TypeScript | עדיפות חזקה ל־UI וובי או תכנית ממשית למערכות הפעלה נוספות | חלופה טובה, לא שדרוג אוטומטי באמינות |
| Electron | צורך מוצדק בסביבת Chromium אחידה ואקוסיסטם Node מלא | לא ברירת המחדל לכלי עזר resident קטן |

Tauri משתמשת ב־Rust וב־WebView של המערכת ומציעה מנגנוני tray, packaging ו־updater עם חתימות חובה. היא מתאימה בהחלט לממשק מעוצב, אך עדיין תצריך adapters ייעודיים ל־Windows; UI רב־פלטפורמי אינו הופך תיקוני COM/WindowsApps לרב־פלטפורמיים. [W12] [W13]

Electron מבוססת על מודל רב־תהליכי של Chromium עם main process בסביבת Node. ההעדפה שלא לבחור בה כאן היא שיקול יחס בין צרכים למורכבות, ולא מדידת RAM או זמן עלייה: benchmarks השוואתיים לא הורצו. [W14]

**איך להכריע בפועל:** לבנות vertical slice אחד שמזהה אפליקציה, מפעיל CLI בטוח, מציג Busy/Partial, ניגש ל־tray ומייצא אבחון. לבדוק אותו ב־DPI גבוה ובעברית. לא לפתח שני מוצרים מלאים כדי לבחור framework.

### אריזה והפעלה

להציע קובץ התקנה או launcher מזוהה אחד, הפעלה ללא קונסולה, הסרה דרך המנהל וקיצור קבוע. להפסיק לבסס את כל מסלול הפתיחה על VBS: Microsoft מתעדת תהליך הוצאה הדרגתי של VBScript משימוש. אין צורך לחכות להסרה מלאה כדי לבטל את התלות. [W15]

חתימת קוד חשובה לזהות המפרסם, אך אינה הבטחה ש־SmartScreen לעולם לא יציג אזהרה לקובץ חדש. לא להדריך משתמשים לכבות Defender או להוסיף החרגה גורפת כדי שהמוצר יעבוד. [W16]

## 6. חוויית המשתמש שכדאי לבנות

### מסך ראשון: מה נמצא ומה אפשר לעשות

במקום dropdown שמתחיל ב־Codex ושטח לוג גדול, להציג כרטיסים של האפליקציות שזוהו. בכל כרטיס: הגרסה המדויקת, רמת תאימות, המצב הנוכחי ופעולה ראשית אחת. אפליקציות שלא נמצאו יופיעו באזור משני, לא ככשל.

רמות מוצעות: **נבדק בגרסה זו**, **טרם נבדק**, **נמצא שינוי לא נתמך**, **התאמה ניסיונית**, **אין צורך בהתאמה**. אין להשתמש בירוק רק משום ש־exe נמצא.

### לפני התקנה: חוזה שינוי ברור

להציג מה ישתנה, כמה מקום צריך, מה יישמר, האם יש פרופיל משותף והאם יהיה צורך לסגור את האפליקציה. ב־Codex יש גילוי נאות על השינוי ב־asar-integrity בעותק. ב־Herdr יש גילוי נאות על שימוש ב־fork נפרד.

כבר יש מנגנוני אבחון של נפח וזיהוי; צריך להעלות את המידע הרלוונטי אל מסלול ההתקנה, לא לבנות פיצ'ר אבחון חדש בשם אחר. [R3]

### בזמן פעולה: progress אמיתי ומצבים ברורים

להציג שלבים ממשיים: מכין, מעתיק, מחיל, מאמת, מוכן. להבדיל בין אחוז מוערך להתקדמות מדידה. כפתור ביטול פעיל רק בנקודות שבהן ניתן לבטל בלי להשאיר מערכת לא עקבית; בזמן swap עדיף להסביר שהפעולה משלימה שלב קצר, ולא להרוג תהליך באמצע.

לוגים, hash ונתיבים יהיו תחת "פרטים טכניים". המסך הרגיל יענה: מה קורה עכשיו, האם צריך ממני משהו, ומה לעשות אם נכשל.

### אחרי פעולה: לוודא שהתוצאה שימושית

כפתור "פתח עם תמיכת עברית", דוגמת משפט מעורב עם קוד ודרך קצרה לדווח "לא נראה תקין". בדיקת runtime צריכה להיות ממוקדת ומוגבלת; לא לפתוח CDP נגיש ברשת או להשאיר פורט debugging פתוח כחלק ממוצר רגיל.

### הסרה והתאוששות

מסך אחד שמבדיל בין הסרת התאמה, שמירת מידע אישי, ניקוי מטמון וניקוי שאריות. `CleanupPending` הוא מצב מוצר לגיטימי עם פעולה גלויה. יש לשמור גישה אל "פתח את המקור" כאשר העותק חסום, ולהזהיר כשהעותק מפגר אחרי גרסת המקור במקום להציג אותו כעדכני.

## 7. יכולות נוספות שכדאי לתעדף

### עדיפות גבוהה: בתוך המוצר המרכזי

**מטריצת תאימות חיה אך מאומתת.** לזהות גרסת app/layout ולתעד מועד וסוג בדיקה. מניפסט תאימות צריך להיות חתום או להישלח כחלק מגרסה מאומתת, ולא להפוך למסלול הרצת קוד מרחוק שרירותי.

**מצב בטוח וחזרה לגרסה קודמת.** מצב מצומצם לשינוי direction בלבד, יחד עם rollback מוגבל ומסומן. אין להקפיא ללא ידיעת המשתמש עותק ישן אחרי שהמקור כבר קיבל עדכון.

**הגדרות עם תצוגה מקדימה.** כבר קיימים policy, משטחים וגופן. השדרוג הוא preview של עברית, אנגלית, קוד, טבלה ומתמטיקה; חיבור נכון בין toggle להתנהגות; ואפשרות השבה לברירת מחדל. [R3] [R7]

**אבחון מובן למשתמש.** חבילת האבחון הקיימת היא נכס. להוסיף preview לפני שיתוף, בדיקות redaction ותיאור מה נכנס. לא להבטיח שכל מחרוזת סודית אפשרית מזוהה באמצעות regex. לא לאסוף שיחות או clipboard ברקע. [R3]

### עדיפות שנייה: לבדוק ביקוש לפני בנייה

**קיצור זמני לשינוי כיוון במשטח הנוכחי**, רק באפליקציות שבהן ניתן ליישם זאת בלי לגעת בקוד או בתוכן.

**העתקה וייצוא נכונים לעברית** של טבלאות, Markdown וקטעים מעורבים, לפי פעולה מפורשת. טקסט קוד חייב להישאר byte-for-byte ככל שהפורמט מאפשר; אין להחדיר בשקט תווי כיווניות לתוך פקודות או קבצים.

**הרחבת דפדפן על בסיס אותה ליבת RTL**, כאשר משתמשים מבקשים אותה. כבר קיימים תוספים שמציעים RTL ל־ChatGPT, כך שזה אינו שוק ריק. עצם קיום listing אינו הוכחה לאיכות, לגודל השוק או להכנסות. [W17]

**תרומות upstream לפרויקטים פתוחים.** לעיתים תיקון במקור עדיף על תחזוקת fork. כשהתמיכה המקורית מספיקה, המנהל צריך לדעת לא להתקין patch מיותר. זהו עיקרון מוצר, לא טענה שהתמיכה כבר שלמה בכל גרסה.

### מה לא לבנות כרגע

לא לקוח צ'אט חדש עם כל ספקי המודלים; לא מערכת חשבונות ותשלומים; לא סנכרון שיחות; לא תרגום אוטומטי של כל UI; לא ניטור clipboard קבוע; לא plugin marketplace שמקבל קוד לא בדוק; ולא תמיכה בכל אפליקציה רק מפני שנראה שאפשר להזריק אליה JavaScript.

## 8. אסטרטגיית הפצה וקהילה

### קהל ראשון

מפתחים ומשתמשים מתקדמים ב־Windows שעובדים בעברית עם קוד, פקודות, נתיבים וטבלאות. לקהל זה קל יותר להסביר מגבלות תאימות, והוא יכול להחזיר דיווח איכותי. הפצה לכל משתמשי המחשב דוברי העברית היא שלב מאוחר יותר.

בבטא עדיף להתחייב לשניים או שלושה adapters שנבדקו בגרסאות רלוונטיות, ולסמן את היתר כניסיוניים. מספר האפליקציות אינו מדד איכות. Herdr ראויה למסלול נפרד בשל build של fork, פרופיל נפרד והבדלים בין עברית לערבית המתועדים ב־README. [R9] [R10]

### מה להראות בדף הפרויקט

הדגמה קצרה של אותו משפט לפני/אחרי; הורדה ראשית אחת; טבלת תאימות לפי גרסה; הסבר מפורש שאין צורך למסור חשבון AI לכלי; הוראות שחזור; ומגבלות שמתאימות בדיוק ל־release. כבר קיימים README מפורט, disclaimer ונכסי תצוגה: צריך לערוך ולסנכרן אותם, לא להחליפם בטקסט שיווקי ארוך יותר. [R10]

להוסיף מסלול דיווח ברור עם OS, גרסת app, גרסת adapter, מצב הפעולה ותוצאה צפויה. SECURITY.md מגדיר ערוץ לדיווח רגיש; CONTRIBUTING.md מתאר הוספת adapter ופקודת בדיקות. אין צורך להעלות למערכת issue אוטומטית מידע מהמחשב בלי preview ואישור.

### ניסוי שימוש מוצע

להזמין קבוצה מוגדרת של 10–20 משתמשים מתקדמים, ואז קבוצה קטנה שאינה מכירה את הפרויקט. אלה גדלי ניסוי מוצעים, לא חישוב עוצמה סטטיסטית ולא נתוני אימוץ קיימים.

למדוד האם המשתמש התקין ללא עזרת המפתח, הגיע לתצוגת עברית תקינה, הצליח להסיר והתקין שוב. לתעד את מספר בקשות התמיכה ואת סוגי התקלות. downloads ו־stars אינם תחליף להפעלה מוצלחת.

**שער הרחבה מוצע:** אין מקרים ידועים של פגיעה בנתונים; כל בדיקות ההתאוששות הקריטיות עברו; כל המשתמשים שנכשלו קיבלו דרך ברורה לחזור למצב תקין; ומשתמשים חדשים משלימים את המסלול ללא הנחיות אישיות. יעדי אחוזי הצלחה יוגדרו מראש, וידווחו יחד עם גודל המדגם.

## 9. תכנית בדיקות ושחרור

| רובד | מה לבדוק | מה אינו מחליף אותו |
|---|---|---|
| סטטי ויחידות | parsing, קידוד, schema, parsing של commands, retry classification, result contracts | ביקורת AI בלבד |
| אינטגרציה ב־Windows | locks, junctions, Registry מבודד, receipt, partial cleanup, קריסה בזמן swap | fixtures של JavaScript בלבד |
| renderer בדפדפן | streaming, DOM reuse, mixed bidi, inputs, copy/paste, screenshots ו־DOM assertions | בדיקת קיום script tag |
| חבילת שחרור | בנייה נקייה, כל הקבצים הנדרשים, גרסאות תואמות, חתימות ואימות עדכון | checksum על ZIP מקומי שלא הורץ |
| E2E על אפליקציות אמיתיות | פתיחה, RTL, עדכון מקור, uninstall/reinstall, fallback | `-SelfTest` שבונה טופס בלי להציגו |

הבדיקות האוטומטיות חייבות לעבוד על roots ושמות אירועים ייחודיים. בדיקת named event אינה רשאית לשלוח אות סגירה למגש האמיתי של המפתח. Registry fixtures משתמשים במפתחות בדיקה בלבד. אין להכניס profiles, tokens או בינארים של צד שלישי ל־fixtures הציבוריים.

מטריצה ראשונית: Windows נתמך לפי הגדרה מפורשת, משתמש רגיל ללא admin, שם משתמש עברי, DPI מוגדל, OneDrive/הפניית תיקיות, מעט מקום פנוי, offline, קובץ נעול, state פגום, מקור שהוסר ומקור שהתעדכן. לא להכריז על ARM64 או macOS/Linux עד שנבדקו.

Pipeline מוצע: PR checks → build נקי מאותו commit → package validation → Windows integration → יצירת artifacts ו־attestation → preview release → אישור אנושי להפצה יציבה. פרטי בדיקות חיות שאינן ניתנות להרצה ב־CI יתועדו בנפרד עם גרסאות, תאריך ותוצאה, ולא יוצגו כ־CI שעבר.

## 10. איך להשתמש ב־ASTRA בלי להפוך זאת לשכתוב בלתי נשלט

המודל יכול לבצע ריפקטורינג משמעותי. נכון לנצל אותו בעיקר להפקת בדיקות, הגדרת חוזים, סגירת מסלולי כשל והגירה מדורגת. יכולת לכתוב הרבה קוד אינה ראיה שקוד נבדק על Windows נקי.

| חבילת עבודה | תוצאה נדרשת | תנאי מעבר |
|---|---|---|
| A. תיקוני release | F01–F07, receipt, תוצאות עקביות, קידוד ו־README | בדיקות כשל והתאוששות משחזרות ועוברות |
| B. שערי איכות | workflow, packaging fail-fast, checksums קשורים ל־asset, provenance | build חוזר מאותו commit והוכחות בדיקה זמינות |
| C. חוזי מנוע | AppContext, operation results, adapters ו־state כתוב אטומית | CLI והאשף הישן משתמשים באותו חוזה |
| D. renderer regression | מקרה לכל toggle, streaming, reuse ו־safe mode | אין רגרסיה בקוד, selection או logical order |
| E. מנהל Windows | vertical slice ולאחריו מסכי manager ו־tray | עובד מול המנוע הקיים על Windows נקי |
| F. הגירה והרחבה | מעבר adapter אחד בכל פעם, ערוץ beta, הרחבות לפי ביקוש | parity, rollback וראיות לגרסאות נתמכות |

אפשר לקדם תיעוד, fixtures ו־UI במקביל, אבל לא להפעיל כמה סוכנים שמשנים במקביל אותו חוזה state או את ליבת ההתקנה ללא בעלות ברורה. לכל PR: מה משתנה, איזה סיכון נסגר, איזו בדיקה נכשלת לפני התיקון ועוברת אחריו, ואיך חוזרים לאחור. אין tag, release או פעולה במחשבים אמיתיים רק משום שהקוד נבנה בהצלחה.

## 11. מסקנה

**הפרויקט ראוי להמשך ולהפצה מבוקרת. השיפור החשוב ביותר אינו עוד פיצ'ר RTL או framework חדש, אלא אמינות ההתנהגות כשהכול אינו מצליח.**

לאחר סגירת מסלולי אובדן נתונים, הסרה חלקית, תוצאות שקטות והגנת הנתיבים, יש בסיס טוב לבטא. אחר כך מנהל Windows עצמאי יכול לשנות משמעותית את חוויית המשתמש. השכתוב צריך להחליף את התלות ב־globals וב־launchers שבירים, לא למחוק את הידע שכבר נצבר בהתאמות.
